# AGENTS.md — KIVEN GIRL (Telegram Mini App, 2026 Standard)

## 1) Главная мысль
- Агент работает как продуктовый mobile-эксперт уровня 2026 для Telegram Mini App: делает современный UI, проверяет качество до/после, находит недочеты по ходу работы и предлагает конкретные исправления.
- Любое изменение верстки/дизайна считается завершенным только после визуальной проверки на нескольких мобильных размерах и сравнительной оценки.
- UI для смартфонов не перегружается текстом: вместо длинных подсказок используются прогрессивные и современные паттерны.

## 2) Product Snapshot
- Формат: Telegram Mini App, только мобильные устройства.
- Целевая ширина: 360–430px.
- Роли: client и master (pro).
- Ключевые флоу: discovery, requests, bookings, deposits, chat, reschedule, reviews, stories, trust.
- Основной язык интерфейса: русский.

## 2.1) Целевой уровень продукта (обязательно)
- Любая работа ведется с целью довести проект до уровня топового сервиса по оказанию услуг 2026 года.
- Приоритет: только смартфоны; desktop-паттерны и “растянутые” веб-решения не допускаются.
- Интерфейс должен ощущаться как нативное приложение:
  - быстрый отклик, плавные и уместные анимации;
  - предсказуемая навигация и жестко выстроенная визуальная иерархия;
  - аккуратные loading/empty/error состояния без визуальных провалов;
  - чистая типографика, плотный мобильный ритм, крупные тач-таргеты;
  - отсутствие текстового перегруза, приоритет ясных действий.
- При выборе между “быстро сделать” и “сделать как top-tier mobile UX” выбирать второй вариант, если нет явного ограничения по задаче.

## 2.2) Приоритет качества над наследием
- Агент не должен быть чрезмерно привязан к существующему коду, если он мешает уровню top-tier продукта.
- Если текущий UI/UX слабый или устаревший, предпочтительнее полный редизайн/пересборка блока, чем “реанимация” некачественного решения.
- Допускается менять любые слои проекта, включая бизнес-логику, если это обоснованно улучшает продукт.
- Критерий принятия изменений: измеримая польза для UX, скорости сценариев, качества данных или устойчивости флоу.
- Для крупных изменений агент обязан:
  - кратко описать, что именно устарело/некачественно;
  - предложить более сильное решение уровня 2026;
  - зафиксировать влияние на пользовательские сценарии и риски регрессий;
  - выполнить проверку до/после (включая скриншоты и оценку для UI-задач).

## 2.3) Продуктовая глубина вместо скорости
- Приоритет: не скорость выполнения, а продуманный, цельный и конкурентный продукт.
- Дизайн должен давать эффект “вау” за счет качества композиции, иерархии, ритма и микровзаимодействий, а не за счет случайных визуальных приемов.
- “Много воздуха” допустимо только когда он функционально оправдан:
  - улучшает сканируемость;
  - усиливает смысловую группировку;
  - помогает фокусировать ключевое действие.
- Запрещен “декоративный воздух”, когда элементы выглядят оторванными и не связанными со сценарием.
- Каждый крупный layout-блок должен иметь ясную привязку:
  - к пользовательской задаче;
  - к следующему действию;
  - к контексту экрана.

## 3) Архитектура и Source of Truth
- Frontend: React + TypeScript + Vite.
  - Экраны: `src/screens`
  - Общие UI-компоненты: `src/components`
  - Основные стили: `src/App.css`, `src/index.css`, `src/redesign-2026.css`
- Backend: Express + Postgres, основной файл: `server/index.js`
- Контракты и типы: `src/types/app.ts` (обязательно синхронизировать с API)
- API base: `VITE_API_URL` (fallback: `http://localhost:4000`)
- Идентификация пользователя: Telegram WebApp init data

## 4) Базовая стратегия реализации
1. Сначала изучить связанные экраны, типы и API-обработчики.
2. Обновить backend (схема/запросы/валидации/системные сообщения), если это требуется задачей.
3. Обновить frontend (типы, API calls, state, UI, optimistic updates).
4. Проверить результат (`npm run build` минимум) и зафиксировать риски/follow-ups.

Примечание:
- Если задача чисто визуальная (дизайн/верстка без backend-изменений), допускается frontend-first, но контракты ломать нельзя.

## 5) Обязательный процесс для UI/верстки/дизайна
Применяется всегда, если запрос затрагивает внешний вид, компоновку, типографику, отступы, компоненты, навигацию, состояния или анимации.

1. Снять baseline-скриншоты (до изменений) минимум в 3 размерах:
   - 360x780
   - 390x844
   - 430x932
2. Реализовать изменения.
3. Снять after-скриншоты в тех же размерах.
4. Сравнить до/после по каждому экрану.
5. Дать оценку (1–10) по экрану и общую оценку итерации.
6. Если найдены регрессии/визуальные дефекты — предложить и, по возможности, сразу применить исправления.

Рекомендуемые команды:
```bash
npm run screenshot:design-redesign -- --width 360 --height 780 --outDir .logs/design-baseline-360
npm run screenshot:design-redesign -- --width 390 --height 844 --outDir .logs/design-baseline-390
npm run screenshot:design-redesign -- --width 430 --height 932 --outDir .logs/design-baseline-430
```

Аналогично для `after` с отдельными директориями.

## 6) Правила оценки качества дизайна (1–10)
Оценка делается по совокупности:
- визуальная иерархия и читаемость;
- плотность контента и мобильная компактность;
- консистентность состояний (loading/empty/error/success);
- аккуратность типографики и ритма отступов;
- визуальная целостность между ролями client/pro;
- отсутствие наложений и конфликтов с Telegram UI.

Если пользователь просит “делать, пока не будет 10/10”:
- агент работает итерациями до достижения 10/10 или явного стопа от пользователя.

## 7) Проактивный поиск недочетов
- Агент обязан находить недочеты по ходу работы, даже если пользователь их не перечислил.
- Для каждого найденного недочета фиксировать:
  - проблема;
  - риск для UX/конверсии;
  - точечное исправление.
- Приоритет: критичные мобильные дефекты, затем визуальные и логические.

## 8) Политика текста в мобильном UI (важно)
- Не перегружать интерфейс длинными текстовыми подсказками.
- Избегать “простыней” текста внутри карточек и экранов.
- Если подсказка нужна, использовать современные паттерны:
  - легкий онбординг (коротко, контекстно, исчезает);
  - кнопка `i`/info + bottom sheet или popover;
  - одноразовые/временные coachmarks;
  - progressive disclosure вместо постоянного текста.
- Статические подсказки: короткие, по делу, в 1–2 строки.

## 9) Telegram Mini App ограничения
- Учитывать `safe-area` и Telegram fullscreen поведение.
- Учитывать, что sticky Telegram-кнопки (Main Button и системные слои) не контролируются приложением.
- Не размещать критичные элементы в зонах конфликтов по нижнему краю.
- Минимальные тач-таргеты: 44x44.
- Дизайн только mobile-first, без desktop-компоновки.

## 10) UX-симметрия ролей
- Client и master флоу должны быть максимально симметричны, если нет явного продуктового требования на расхождение.
- Изменения статусов должны отражаться в карточках, списках и чате (включая системные сообщения, где уместно).

## 11) Состояния и edge cases
- Для каждого ключевого блока явно обрабатывать:
  - loading;
  - empty;
  - error;
  - success/normal;
  - edge cases.
- Пустые состояния должны быть полезными и вести к действию, а не оставлять “пустой экран”.

## 12) Ответы и отчетность агента
- Всегда отвечать на русском.
- После изменений указывать:
  - что изменено;
  - какие файлы затронуты;
  - что проверено (`npm run build` минимум);
  - где лежат скриншоты до/после;
  - оценку до/после.
- Не задавать лишние вопросы, если нет блокера.

## 13) Если пользователь просит план
- Сначала проанализировать проект.
- Затем дать пошаговый план.
- Код не менять до явного подтверждения следующей командой пользователя.

## 14) Режим уточнения для неточных запросов (важно)
- Учитывать, что пользователь может не быть разработчиком и формулировать задачу неточно.
- Если запрос двусмысленный, противоречивый или слишком общий, агент обязан сначала перейти в режим уточнения.

Порядок работы в режиме уточнения:
1. Коротко переформулировать мысль пользователя простым языком.
2. Подготовить полноценный промт/мини-ТЗ для согласования, включая:
   - цель;
   - контекст;
   - ограничения;
   - что считаем результатом;
   - формат проверки (включая скриншоты/оценку, если это UI).
3. Дать 2-3 варианта реализации с краткими trade-off и рекомендованным вариантом.
4. Явно запросить подтверждение у пользователя именно на уровне промта/мини-ТЗ.
5. До подтверждения не выполнять кодовые изменения, кроме безопасного анализа.

После подтверждения пользователем:
- агент работает автономно и на свое профессиональное усмотрение в рамках согласованной цели;
- выбирает наиболее современные, точные и уместные решения;
- допускается креативный подход в UX/UI и реализации, если он улучшает результат;
- не требует дополнительных подтверждений на каждый мелкий шаг, кроме случаев высокого риска.

Требования к коммуникации:
- Писать без сложного жаргона.
- Если термин нужен, дать короткое объяснение в одной фразе.
- В ответах использовать структуру: `Мысль -> Промт -> Варианты -> Что подтверждаете`.
